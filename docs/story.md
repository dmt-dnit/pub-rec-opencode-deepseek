# Build Smart With Agents

Track A started with a familiar technical target and an unfamiliar process target. The app itself was not exotic: JWT-based SSO, two Spring Boot services, a Kafka choreographed saga, and two Angular SPAs. A customer places an order, inventory reserves stock, and both dashboards update live. The unusual part was how the project was built. Instead of one developer or one long AI session, the repo used three roles on purpose: an implementer, a coordinator, and an independent reviewer.

That separation matters because most AI demos hide the part that makes real work expensive: plausible changes that are still wrong. In this repo, `opencode + DeepSeek` implemented one brief at a time. Claude coordinated: wrote the sprint briefs, checked the diffs, reran the right commands, and wrote handoffs. Codex reviewed independently and either cleared the sprint or rejected it with concrete blockers. The system being built mattered, but the stronger artifact was the loop that forced claims to survive another role.

Sprint 1 established why that workflow was necessary. Early work happened in one shared tree, and concurrent edits contaminated files across the order/inventory rename. Codex rejected the sprint with real blockers: stale frontend proxy paths, broken inventory test wiring, a lazy Hibernate serialization failure on the WebSocket path, and noisy dependency posture. The lesson was not subtle. If multiple agents touch a broad refactor in the same working tree, speed turns into ambiguity. Isolated worktrees became a rule, not a preference.

Sprint 4 exposed a second failure mode: the handoff had outrun reality. Two of five tasks were still unstarted when the repo reached review, and there was no reliable commit checkpoint proving what state was actually under review. That failure created `scripts/pre-review-check.sh`, which now fails closed if the working tree is not committed or the handoff doc is missing. It is a small script, but it marks an important change in posture: do not trust an implementation report, prove that the state is reviewable before asking for a verdict.

The most honest failure came in Sprints 9 and 10. After the team removed the SockJS crash, the dashboards still did not render live state. The Sprint 9 fix added `provideZoneChangeDetection()` and wrapped STOMP callbacks in `NgZone.run()`, both of which were reasonable. The coordinator also removed `ChangeDetectionStrategy.Eager` from the order dashboard as "code hygiene." Under Angular 22 that assumption was wrong. The installed Angular code effectively treated the omitted value as OnPush in this setup, so HTTP and WebSocket state changed but the view was not marked the way the team expected. Sprint 10 restored `Eager` and cleared part of the issue. That is the most credible conference beat in the whole repo: the coordinator introduced a real regression while trying to tidy code, and the reviewer caught it.

Even then, the browser gate stayed open. Sprint 10 made `order-ui` render orders again, but `inventory-ui` still showed an empty Material table while `/api/inventory` returned real SKU rows. Sprint 11 fixed that with `MatTableDataSource`, and the way it was found matters as much as the code. Static builds and TypeScript checks were green. The API was correct. The component assignments were happening. The browser still showed an empty table. The fix only became obvious when the team treated the rendered UI as the source of truth instead of treating passing builds as a proxy for correctness.

Sprints 11 through 13 then turned into a locator and state-discipline story. The first Playwright smoke used broad `.order-header` and `.badge-confirmed` selectors. A non-empty local database meant old orders were still present, so strict locator matching failed. The next attempt scoped the card too loosely and matched the outer Orders container because of descendant matching. Sprint 13 finally added `data-testid="order-card"` to the repeated card and updated the smoke to wait on the count of those repeated cards, then assert inside the newest one. That sequence is one of the most reusable lessons in the repo: selector correctness is part of product correctness, and end-to-end tests should assume dirty state unless they explicitly own the reset.

Track A closed when the browser smoke passed end-to-end against a non-empty local database: log into both UIs, see seeded SKUs, place a `SKU-001` order, watch the order move to `CONFIRMED`, see a `RESERVED` feed event, and confirm the inventory decrement. That closure matters, but the stronger result is what the retro forced into policy: acceptance criteria now describe observable outcomes, not implementation steps; browser-required work is labelled as such; handoffs include actual command output and explicit limitations; and the reviewer path stays source-edit free.

Track B reinforced those rules in other domains. Sprint 14 showed that local green is not target green when Linux CI metadata can still be wrong. Sprint 15 showed that hosted CI green is not runtime green when a hardcoded JWKS URL breaks JWT validation inside containers. Sprint 16 showed that runtime green is not dependency/security green until the scanner gate itself is proven live, which eventually required swapping a broken OWASP job for Snyk SCA and verifying the real CI run. Sprint 17 adds the next refinement: exactly-once claims must be validated at the observable boundary. A Kafka Testcontainers test can look real while still wiring its lifecycle incorrectly, and a transactional outbox can improve DB crash safety while still duplicating the inventory feed if the relay also owns the STOMP push.

That is the practical meaning of "build smart with agents" in this repo. First, separate implementation, coordination, and review so one voice is not grading itself. Second, define acceptance at the boundary the user or operator actually experiences. Third, keep the failures in the narrative instead of cleaning them out afterward. The Sprint 9/10 Angular regression, the selector failures in Sprints 11-13, the Track B CI/runtime/security catches, and the Sprint 17 exactly-once caveat are not embarrassing detours. They are the evidence that the workflow became capable of proving itself wrong, which is the only reason its eventual green runs mean anything.
