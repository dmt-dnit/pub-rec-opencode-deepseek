# Task G-1: Add a working `mvnw.cmd` to all 4 Maven modules

**Resolves:** Must-fix 3 in `reviews/sprint-2-track-a-review.md` ("The Maven wrapper is still not usable from Codex's Windows PowerShell environment... each backend module ships only a bash `mvnw` script... `.\mvnw.cmd` is not present").

## Context

`shared-model`, `auth-server`, `order-service`, and `inventory-service` each have an `mvnw` (bash) script but no `mvnw.cmd`. On Codex's Windows/PowerShell environment, `.\mvnw -q test` fails outright with `Access is denied`, and there's no `.cmd` fallback to try instead. This has been flagged twice now (Sprint 2's handoff already called out `./mvnw` problems, and this re-review confirms the Windows side specifically is still unaddressed) — every other fix in this sprint is worthless to Codex if it can't actually invoke Maven to check it.

## Task

Generate the standard Maven Wrapper for all 4 modules so each one has both `mvnw` (bash) and `mvnw.cmd` (Windows), plus the `.mvn/wrapper/` support files they both need:

```
cd shared-model && mvn -N wrapper:wrapper -Dmaven=3.9.9
cd ../auth-server && mvn -N wrapper:wrapper -Dmaven=3.9.9
cd ../order-service && mvn -N wrapper:wrapper -Dmaven=3.9.9
cd ../inventory-service && mvn -N wrapper:wrapper -Dmaven=3.9.9
```

Pin the same Maven version across all 4 modules — they're meant to build consistently, divergent wrapper versions between modules is its own kind of drift to avoid. Check the existing `.mvn/wrapper/maven-wrapper.properties` in each module first (added 2026-06-19 per `CLAUDE.md`) to see what Maven version is already targeted, and keep that version unless there's a reason to change it — don't introduce an unrelated version bump as a side effect of this task.

Do not hand-write `mvnw.cmd` from scratch or copy one from memory — generate it via the `wrapper:wrapper` goal (or copy the exact file Maven's own wrapper plugin produces) so it matches the checksums/URLs `maven-wrapper.properties` expects.

## Out of scope
- Don't change the pinned Maven version unless the currently-configured one is broken — that's a separate concern from "the Windows script doesn't exist."
- Don't touch the Java toolchain enforcer config from G-7/F-7 — unrelated.

## Acceptance criteria
- All 4 modules have both `mvnw` and `mvnw.cmd` at their root, generated by the Maven wrapper plugin (not hand-written).
- On Linux/macOS, `./mvnw -v` still works in all 4 modules (the bash script must not regress).
- On Windows (or by inspection if no Windows machine is available — confirm the script matches Maven's known-good wrapper template), `.\mvnw.cmd -v` resolves and reports the same pinned Maven version as the bash script.
- `git diff` shows no unrelated changes to `pom.xml` or other build config in this task.
