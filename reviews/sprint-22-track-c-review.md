# Sprint 22 Track C Review - Deploy Artifacts

Verdict: REJECT — deploy security and proxy-scoping issues remain

## Findings

- **[P1] The deploy workflows blindly trust whatever SSH host key is presented at runtime, which makes the production deploy path MITMable.** All three workflows append `ssh-keyscan -H "$VPS_HOST"` directly into `~/.ssh/known_hosts` at [.github/workflows/deploy-auth.yml](C:/projects/pub-rec-opencode-deepseek/.github/workflows/deploy-auth.yml:70), [.github/workflows/deploy-order.yml](C:/projects/pub-rec-opencode-deepseek/.github/workflows/deploy-order.yml:70), and [.github/workflows/deploy-inventory.yml](C:/projects/pub-rec-opencode-deepseek/.github/workflows/deploy-inventory.yml:70). That is trust-on-first-use inside CI, not host verification. An attacker who can intercept DNS or network traffic during a workflow run can supply a different host key, receive the uploaded jar and deploy script, and execute arbitrary remote commands under the deployment identity. The host fingerprint needs to be pinned out-of-band, for example via a committed `known_hosts` entry or an environment secret containing the expected fingerprint.

- **[P2] The Nginx WebSocket upgrade headers are not actually scoped to the WebSocket endpoint; they apply to every request on the order and inventory hosts.** The handoff claims the upgrade behavior is correctly limited to the two services that expose `/ws`, but the config places `proxy_set_header Upgrade` and `proxy_set_header Connection "upgrade"` inside the catch-all `location /` blocks at [deploy/nginx/saga-orders.conf](C:/projects/pub-rec-opencode-deepseek/deploy/nginx/saga-orders.conf:18), [deploy/nginx/saga-orders.conf](C:/projects/pub-rec-opencode-deepseek/deploy/nginx/saga-orders.conf:21), [deploy/nginx/saga-orders.conf](C:/projects/pub-rec-opencode-deepseek/deploy/nginx/saga-orders.conf:22), [deploy/nginx/saga-inventory.conf](C:/projects/pub-rec-opencode-deepseek/deploy/nginx/saga-inventory.conf:18), [deploy/nginx/saga-inventory.conf](C:/projects/pub-rec-opencode-deepseek/deploy/nginx/saga-inventory.conf:21), and [deploy/nginx/saga-inventory.conf](C:/projects/pub-rec-opencode-deepseek/deploy/nginx/saga-inventory.conf:22). In the application code, the actual WebSocket endpoint is only `/ws` at [order-service/src/main/java/com/example/orderservice/config/WebSocketConfig.java](C:/projects/pub-rec-opencode-deepseek/order-service/src/main/java/com/example/orderservice/config/WebSocketConfig.java:21) and [inventory-service/src/main/java/com/example/inventoryservice/config/WebSocketConfig.java](C:/projects/pub-rec-opencode-deepseek/inventory-service/src/main/java/com/example/inventoryservice/config/WebSocketConfig.java:21), with matching security allowance at [order-service/src/main/java/com/example/orderservice/config/SecurityConfig.java](C:/projects/pub-rec-opencode-deepseek/order-service/src/main/java/com/example/orderservice/config/SecurityConfig.java:28) and [inventory-service/src/main/java/com/example/inventoryservice/config/SecurityConfig.java](C:/projects/pub-rec-opencode-deepseek/inventory-service/src/main/java/com/example/inventoryservice/config/SecurityConfig.java:28). The proxy config should either add a dedicated `location /ws` block or use a conditional `Connection` mapping so ordinary HTTP requests do not carry forced upgrade semantics.
